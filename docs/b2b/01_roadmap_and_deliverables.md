# SY Valuation — B2B API 로드맵 및 필수 산출물

작성일 2026-11-25 · 대상: 증권사 WM/IB, 자산운용사, 대기업 전략기획팀 대상 「기업가치평가 계산 엔진 API + MCP 서버」 판매

---

## 1. 한 줄 포지셔닝

> **"LLM 이 말하고, 숫자는 SY 엔진이 계산한다."**
> 사내 AI 에이전트가 기업가치를 물을 때 호출하는, 재현 가능하고 근거가 추적되는 계산 엔진.

조회형 데이터 API(재무·시세)는 이미 FnGuide·KIS·DART 가 판다. 우리가 파는 것은 데이터가 아니라 **계산 계약**이다: 같은 입력이면 같은 결과, 모든 숫자에 산식과 출처가 붙는다.

## 2. 현재 구조 진단 (코드 기준)

| 영역 | 현재 상태 | B2B 관점 평가 |
|---|---|---|
| 계산 엔진 | `valuation/sy_method.py` (3접근법·11개 산식), `valuation/engine.py` (9-모델) — 순수 함수, 외부 의존 없음 | **핵심 자산.** 데이터 수집과 분리돼 있어 그대로 상품화 가능 |
| 데이터 | DART TTM → Naver TTM → 샘플 순 폴백, 가격은 Naver/Yahoo | 폴백이 조용히 일어남. B2B 는 "어떤 데이터로 계산했는지" 가 계약 사항 |
| API | `http.server` 기반 GET 20여 개, 버전·인증·스키마 없음 | 앱 전용. 외부 계약으로 쓸 수 없음 |
| 인프라 | Render 무료 플랜(싱가포르), 단일 프로세스, DART 일 2만 콜 한도 | 금융사 납품 불가 (국내 리전·SLA·격리 요구) |
| 품질 보증 | 테스트 2개 파일 (`test_dart_ttm`, `test_b2b_api`) | "오차 없음" 을 주장할 증빙이 없음 |
| 이번에 추가 | `POST /api/v1/valuations/compute`, `POST /mcp`, OpenAPI, API 키·호출 한도, 시뮬레이터, API 콘솔 | B2B 계층의 첫 골격 |

### 판매 전에 반드시 해결할 4가지 (우선순위순)

1. **엔진 신뢰도.** 시연 중 확인된 값: 삼성전자 DCF 가치 약 5,760조원(시가총액 1,021조원의 5.6배), 종합 +90% STRONG_BUY. 리서치센터장은 이 숫자 하나로 제품을 판단한다. 원인은 단기 성장률 상한 20%·10년 명시기간·`영업이익×10` 고정 배수 등 기본 가정. → 가정 기본값 재보정과 백테스트가 로드맵 1순위.
2. **종합값이 가정에 둔감.** 종합 적정가는 "접근법별 중앙값의 평균"이라 WACC 를 1%p 올려도 DCF 가 중앙값이 아니면 적정가가 0% 변한다. 시뮬레이터에서 그대로 드러난다. → 가중 방식(고객 지정 가중치)을 옵션으로 제공.
3. **데이터 라이선스.** Naver Finance 스크래핑·Yahoo 시세는 상업적 재판매 근거가 없다. B2B 는 (a) DART 공시(공공데이터) + (b) 고객사가 보유한 시세 라이선스(BYO-data) 조합으로 가야 한다.
4. **규제 포지션.** `STRONG_BUY` 등급·"투자 추천" 은 자본시장법상 투자자문/유사투자자문 이슈를 부른다. B2B 상품은 **계산 도구**로 한정하고, 등급·추천은 기본 비활성(옵션)으로 둔다. 법률 검토 필요.

## 3. 로드맵

### 단기 — 0~3개월 (~2027년 2월): "팔 수 있는 최소 계약" 만들기

| # | 과제 | 완료 기준 |
|---|---|---|
| S1 | **엔진 재보정·검증 팩** | KOSPI200 전 종목 골든 테스트(입력→기대값) CI 통과, 수기 엑셀 대조 30개사, 금융업(은행·보험) 전용 경로(DCF 제외·RIM 중심) |
| S2 | **API v1 계약 확정** | `compute` 외 `GET /v1/companies/{ticker}/valuation`, `/financials`, `/peers` · 오류 코드 표준 · OpenAPI 3.1 공개 · 버전 정책(v1 12개월 보장) |
| S3 | **근거 추적(Audit Trail)** | 응답에 `provenance`(DART 접수번호·기준 분기·수집 시각), 모델별 산식·중간값, `input_hash` 로 재현 조회 |
| S4 | **MCP 서버 정식화** | 인증(OAuth 2.1 또는 API 키), 도구 4→8개(재무 조회·피어·민감도·리포트), Claude/사내 에이전트 연동 가이드 |
| S5 | **데이터 정합성 계약** | 조용한 폴백 제거 → `data_quality` 필드(등급 A/B/C)와 `strict=true` 시 폴백 거부. Naver 의존 제거 계획 수립 |
| S6 | **운영 기반** | 국내 리전 이전(AWS 서울/NCP), API 키 발급·사용량 계량(키별 호출 로그), 상태 페이지 |
| S7 | **라이브 쇼케이스** | 앱 내 시뮬레이터·API 콘솔(이번 구현) + 데모 시나리오 3종(리서치·IB·전략기획) |
| S8 | **PoC 2곳 확보** | 증권사 1 + 대기업 전략기획 1, 4주 무상 PoC, 성공 기준 사전 합의 |

## 5. 추가 제안 (요청 범위 밖이지만 넣어야 할 것)

- **"오차율 0%" 표현 교체.** 결정론이 보장하는 것은 *재현성*(같은 입력 → 같은 출력)과 *산식 구현의 정확성*이지, 입력 데이터나 가정의 옳음이 아니다. 금융사 법무는 "0% 보장" 문구를 계약 리스크로 본다. → "계산 재현율 100% · 산식 검증 완료(검증 리포트 첨부)" 로.
- **모델 개수 표기 통일.** 코드에는 SY 평가법(3접근법·11개 산식)과 다중모델(9개)이 따로 있다. 대외 표기는 하나로 정해야 한다. 권장: "3대 접근법 · 11개 산식(+ 고전 모델 4종)".
- **에이전트 평가 세트.** "LLM 단독 vs LLM+SY MCP" 로 같은 질문 50개를 돌려 수치 오류율을 비교한 벤치마크. Problem 슬라이드의 근거가 되고, 그 자체가 콘텐츠 마케팅이다.
- **`llms.txt`·에이전트용 설명.** 도구 설명문이 곧 제품 UX 다. 도구 description 에 단위·기준일·금지사항("재계산하지 말 것")을 명시(이번 MCP 구현에 반영).
- **가격 탄력성 검증.** 가격표는 가설이다. PoC 2곳에서 "호출당" 과 "좌석/인스턴스당" 중 무엇에 예산이 있는지 먼저 묻는다.
- **단일 실패 지점.** DART 일 2만 콜 한도는 B2B 트래픽에서 바로 소진된다. 공시 원문을 자체 저장소에 적재(일 1회 증분)하고 API 는 저장소만 읽도록 바꿔야 한다.
- **운영 배포 주의.** `main` 푸시 시 Render 자동 배포이므로, 이번 변경은 브랜치에서 검토 후 반영.
